## 1. OVERVIEW

Heney is a personal, voice-first AI assistant: a single-page React app that a signed-in
user talks or types to, backed by an Express API that proxies Google Gemini for chat
and ElevenLabs for speech-to-text/text-to-speech. Unlike the original MVP, chat history,
long-term "memories," and reminders are now persisted per-user in Supabase Postgres
with row-level security, gated behind Supabase email/password auth. On top of the raw
Gemini chat, a local "skills" layer intercepts certain message patterns (math, weather,
news, reminders, daily brief, memory/conversation recall) and answers them directly
without calling Gemini. The app is also a basic installable PWA (web manifest, no
service worker found).

**Frontend** (`package.json`, repo root) — name `voice-buddy-frontend`, v1.0.0, ESM (`"type": "module"`):
- `react` ^18.3.1, `react-dom` ^18.3.1
- `@supabase/supabase-js` ^2.108.2
- `@ricky0123/vad-web` ^0.0.30 (client-side voice-activity detection, Silero ONNX models)
- Dev: `vite` ^5.4.11, `@vitejs/plugin-react` ^4.3.4
- Scripts: `dev` (vite), `build` (vite build → `dist/`), `preview`

**Backend** (`backend/package.json`) — name `voice-buddy-backend`, v1.0.0, ESM:
- `express` ^4.21.2, `cors` ^2.8.5, `dotenv` ^16.4.5, `multer` ^2.2.0
- `@google/genai` ^1.0.0 (Gemini SDK)
- `@supabase/supabase-js` ^2.110.7, `express-rate-limit` ^8.6.0 — added in the Phase 0 hardening pass (see §3, §9). The Supabase dependency was previously declared but unused; it now backs a service-role admin client used for JWT verification (`requireAuth`) and `tool_runs` audit logging.
- Scripts: `start` (`node server.js`), `dev` (`node --watch server.js`)

**How the packages relate**: they are two fully independent npm projects (separate
`node_modules`, separate lockfiles) that only communicate over HTTP. In dev, Vite proxies
`/api/*` to `http://localhost:3001` (`vite.config.js`) so the browser can call same-origin
`fetch("/api/...")`. In production there is no proxy — the frontend calls the backend at
an absolute URL from `VITE_API_BASE_URL` (see §7, §8). Neither package imports code from
the other; there is no shared types/schema package. Database access (Supabase) happens
**only from the frontend**, directly from the browser using the public anon key plus RLS —
the backend has no database client at all.

## 2. ARCHITECTURE MAP

### (a) Text chat message (Assistant Mode off, typed input)

```
User types in <textarea> → handleSend() [App.jsx:1404]
  → handleSendMessage(text) [App.jsx:1177]
    1. saveMessage(user.id, conversationId, "user", text)      [lib/conversations.js:71] → INSERT into Supabase `messages`
    2. isStatusPrompt(text)? → formatSystemStatus() short-circuits to a canned status reply
    3. getLocalSkillReply({ userId, message, currentMessageId }) [lib/skills.js:23]
         → tries isCalculatorPrompt / isDailyBriefPrompt / isReminderPrompt /
           isWeatherPrompt / isNewsPrompt / isConversationRecallPrompt / isMemoryRecallPrompt
         → if any matches, returns a string reply WITHOUT calling Gemini
    4. If no skill matched:
       a. rememberFromMessage(user.id, text, messageId) [lib/memory.js:345]
            → POST /api/memory-review (Gemini JSON extraction) → upsertMemory() into Supabase `memories`
       b. getRelevantMemories(user.id, text) [lib/memory.js:386] → ranked memories → formatMemoriesForPrompt()
       c. streamChatMessage(text, history, memoryContext) [lib/api.js:61]
            → POST /api/chat/stream (backend/server.js:728) → Gemini generateContentStream()
            → falls back to sendChatMessage() → POST /api/chat (backend/server.js:690) on stream failure
    5. saveAndSpeakAssistantReply() [App.jsx:1159]
         → saveAssistantReply() INSERTs assistant message into Supabase `messages`,
           UPDATEs `conversations.updated_at`
         → speak(reply) only if speakReplies is on (see voice pipeline below)
```

### (b) Voice interaction, end to end (mic → VAD → STT → skill/Gemini → TTS → playback)

```
Mic capture:
  Web Speech API (SpeechRecognition, App.jsx:454-587) — always running when listening,
  used for a live transcript AND as the VAD-unavailable fallback turn-end signal.
  In parallel, MediaRecorder (App.jsx:623 startTurnRecording) records raw audio for
  ElevenLabs STT, started/stopped by voice-activity events.

VAD (optional, best path):
  ensureVad()/startVad() [App.jsx:859-924] lazily imports @ricky0123/vad-web's MicVAD,
  loading ONNX models from /public/vad/ (baseAssetPath: "/vad/"). Its onSpeechStart /
  onSpeechEnd callbacks drive handleSpeechStart()/handleSpeechEnd() [App.jsx:775-806],
  which start/stop the MediaRecorder and schedule turn completion
  (scheduleTurnCompletion, TURN_END_GRACE_MS ≈1000ms).

Fallback (VAD unavailable):
  recognition.onresult appends to pendingTranscriptRef and
  scheduleFallbackTurnCompletion() fires after FALLBACK_SILENCE_DELAY_MS (2200ms)
  of silence.

Turn completion → resolveVoiceTranscript() [App.jsx:692]:
  1. Prefer server STT: transcribeSpeech(audioBlob) [lib/api.js:136] → POST /api/stt
     (backend/server.js:245) → ElevenLabs speech-to-text API.
  2. On failure/empty, fall back to the Web Speech API's own transcript
     (pendingTranscriptRef, accumulated by recognition.onresult).

  → handleSendMessageRef.current(transcript, { voiceMode: true }) — same
    handleSendMessage() pipeline as (a), with voiceMode:true, which:
      - triggers a spoken "bridge phrase" (speakBridgePhrase, e.g. "On it.") while
        Gemini is still streaming, to mask latency
      - uses createStreamingSpeaker() [App.jsx:1002] to speak completed sentences
        as they stream in from /api/chat/stream, rather than waiting for the full reply

Speech output:
  speak(text) [App.jsx:1088] → splits into sentence chunks (splitSpeechChunks) →
  synthesizeSpeech(chunk) [lib/api.js:159] → POST /api/tts (backend/server.js:310) →
  ElevenLabs text-to-speech → audio/mpeg blob → playAudioBlob() plays via <audio> +
  URL.createObjectURL. While speaking, stopListening() is called so the mic doesn't
  capture Heney's own voice (barge-in support: if the user starts talking while
  speaking, handleSpeechStart() calls stopSpeaking() to interrupt, guarded by
  SELF_INTERRUPT_GUARD_MS=450ms to ignore the assistant's own audio leaking into the mic).
```

### (c) Assistant Mode hands-free loop

```
toggleAssistantMode() [App.jsx:1360]:
  ON  → speakReplies forced true, startVad(), speak greeting once/day
        (shouldSpeakDailyGreeting, localStorage key heney:lastAssistantGreetingDate),
        scheduleListening(100)
  OFF → stopVad(), releaseRecorderStream(), stopListening(), reset state

Steady-state cycle (gated on assistantModeRef.current && !loading && !speaking):
  scheduleListening(delay) [App.jsx:808] → setTimeout → startListening()
    → recognition.start() (SpeechRecognition is continuous=true; each restart is a
      fresh session because recognition.onend always re-arms via scheduleListening
      when Assistant Mode is on)
  → user speaks → VAD/onresult → turn completion → handleSendMessage(..., voiceMode:true)
  → setLoading(true) blocks the listen loop
  → reply arrives → spoken via speak() → finish() callback in speak() calls
    scheduleListening(300) again if resumeListening !== false → loop repeats

This is the same ref-mirror pattern documented in CLAUDE.md: assistantModeRef,
loadingRef, speakingRef, listeningRef, conversationLoadingRef, speakRepliesRef all
mirror their state counterparts via useEffect so the long-lived recognition/VAD
callbacks never close over stale state.
```

## 3. BACKEND API REFERENCE (`backend/server.js`)

**Updated in Phase 0 (hardening).** As of the `phase-0` branch, every route except
`GET /api/health` requires a valid Supabase session JWT, verified server-side. A
`requireAuth` middleware reads the `Authorization: Bearer <token>` header, verifies it
via a service-role Supabase admin client's `auth.getUser(token)`, and attaches
`req.user = { id, email }` on success; missing/invalid/expired tokens get `401
{ error: "unauthorized" }`. CORS is now an explicit allowlist (`http://localhost:5173`,
the production Vercel origin, and a regex for Vercel preview URLs) instead of
`cors()` wide-open; requests from other origins get `403 { error: "cors_rejected" }`
via a dedicated error-handling middleware. `/api/chat`, `/api/chat/stream`, `/api/tts`,
and `/api/stt` are additionally rate-limited per authenticated user (fallback: per IP)
via `express-rate-limit`; over-limit requests get `429 { error: "rate_limited" }`.

| Method & Path | Body / Params | Response shape | External service | Auth | Rate limit |
|---|---|---|---|---|---|
| `GET /api/health` | — | `{ ok: true }` | none | **None** (deliberately public, for uptime checks) | — |
| `GET /api/status` | — | `{ status, backend:{ok,platform}, gemini:{configured,model,ok,detail}, elevenLabs:{configured,ttsModel,sttModel,tts:{ok,detail},stt:{ok,detail}}, supabase:{configured} }` | Live-pings Gemini with a throwaway "Reply with OK only." prompt (`checkGeminiAvailability`); ElevenLabs checks are config-presence only, not live calls | **Required** | — |
| `POST /api/stt` | multipart form, field `audio` (audio file, ≤12MB via multer memoryStorage) | `{ transcript, raw }` or error JSON | ElevenLabs `POST /v1/speech-to-text` (model from `ELEVENLABS_STT_MODEL`, default `scribe_v1`) | **Required** | 30/min/user |
| `POST /api/tts` | JSON `{ text }` | audio/mpeg binary stream, or error JSON | ElevenLabs `POST /v1/text-to-speech/{ELEVENLABS_VOICE_ID}` (default voice id `JBFqnCBsd6RMkjVDRZzb`, model `eleven_flash_v2_5`) | **Required** | 60/min/user |
| `GET /api/news` | query `topic` (free text, mapped to a fixed query string) | `{ topic, articles:[{title,source,publishedAt}] }` (top 5) | Google News RSS (`news.google.com/rss/search`), scraped via regex, **not a real news API** | **Required** | — |
| `POST /api/memory-review` | JSON `{ message, candidates?:[{key,value,confidence,metadata}] }` | `{ shouldRemember, memories:[{key,value,category,confidence}] }` | Gemini (`generateContent` with `responseMimeType: "application/json"`), 10s timeout (`MEMORY_REVIEW_TIMEOUT_MS`) | **Required** | — |
| `POST /api/chat` | JSON `{ message, history?, memoryContext?, voiceMode? }` | `{ reply }`; on Gemini quota error, `200` with `{ reply, errorType:"gemini_quota", degraded:true, ... }` | Gemini `generateContent` | **Required** | 30/min/user |
| `POST /api/chat/stream` | same body as `/api/chat` | NDJSON stream, one JSON object per line: `{type:"chunk",text}` repeated, then `{type:"done",reply}` (or `{type:"error"}`) | Gemini `generateContentStream` | **Required** | 30/min/user |

Notable server-side behavior:
- `buildChatRequest()` assembles Gemini `contents` from `history` (mapping frontend's `assistant`→`model`), appends the new user message, and sets a `systemInstruction` combining a fixed "Heney" persona, an optional voice-mode brevity instruction, and the `memoryContext` string sent by the client.
- Gemini quota/rate-limit errors are detected heuristically (`isGeminiQuotaError`, matching HTTP 429 or text like "quota"/"resource_exhausted") and converted into a friendly degraded reply rather than a hard error, so the frontend can keep working.
- ElevenLabs errors are similarly classified into human-readable `safeReason` values (`invalid key`, `voice unavailable`, `rate limit`, `paid plan required`, `quota exceeded`, `network error`) via string-matching on the response body.
- `/api/status`'s `supabase.configured` field only checks whether `SUPABASE_URL`/`VITE_SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY` env vars are *present* on the backend process — it does not contact Supabase itself for this check.
- **`SUPABASE_URL`+`SUPABASE_SERVICE_ROLE_KEY` are now actually used** (previously dead config, see §9 history): a service-role Supabase admin client backs both `requireAuth` (token verification) and `logToolRun()` (fire-and-forget inserts into `tool_runs`, used by `/api/chat`, `/api/chat/stream`, `/api/tts`, `/api/stt`, `/api/memory-review`, and `/api/tool-run`). This client bypasses RLS by design (service role) and must never be exposed to the frontend.
- `/api/tool-run` exists solely so the frontend's local skills (§5 — calculator, weather, reminders, etc., which never otherwise call the backend) can still get an authenticated, admin-client-backed audit row in `tool_runs`.

**Dead tables**: `profiles`, `calendar_events`, `news_preferences` — schema exists
(with indexes, triggers, RLS) but zero application code references them. This looks
like scaffolding for planned features (calendar sync, per-user news personalization)
that were never wired up. (`tool_runs` was dead at the time of the original inspection
but was wired up in Phase 0 — see above.)

**Code querying tables not in migrations**: none found — every `supabase.from(...)` call
in `src/lib/*.js` (`conversations`, `messages`, `memories`, `reminders`) matches a table
defined in the migration.

**RLS policies in plain English**:
- `profiles`: a user can select/insert/update/delete only their own profile row (`id = auth.uid()`).
- `conversations`: a user can select/insert/update/delete only conversations where `user_id = auth.uid()`.
- `messages`: select/update/delete restricted to `user_id = auth.uid()`; **insert** additionally requires the target `conversation_id` to belong to a conversation owned by the same user (prevents inserting messages into someone else's conversation even if you guessed the ID).
- `memories`, `reminders`, `calendar_events`, `news_preferences`, `tool_runs`: each has one blanket "manage own rows" policy (`FOR ALL USING/WITH CHECK user_id = auth.uid()`) — full CRUD restricted to the owning user.

Since the frontend uses the public **anon key** directly from the browser (no backend
DB proxy — see §1/§9), this RLS is the *only* access control on the data; there is no
server-side enforcement layer at all.

## 5. SKILLS SYSTEM

**Routing (`src/lib/skills.js`)**: `getLocalSkillReply({ userId, message, currentMessageId })`
is called from `handleSendMessage()` in `App.jsx` *after* the user's message is saved
but *before* any Gemini call. It runs a fixed if-else chain of `isXPrompt(message)`
regex/keyword checks, in this order: calculator → dailyBrief → reminder → weather →
news → conversationRecall → memoryRecall. The **first** matching skill's async handler
is awaited and its string return value is used as the final assistant reply — no
further skills are checked and Gemini is never called. If none match, `skills.js`
returns `""`, and `handleSendMessage()` falls through to the memory-context-augmented
Gemini call (§2a). There is also one skill-like check that lives directly in
`App.jsx` rather than `skills.js`: `isStatusPrompt()` (fixed phrases like "heney
status"), checked even before `getLocalSkillReply`.

**Skill contract**: each skill module exports (at minimum) an `isXPrompt(message):
boolean` matcher and either a sync/async `getXReply(...): string` or, for skills
needing to write data, a combined handler (e.g. `handleReminderPrompt`). Handlers
receive whatever arguments `skills.js` chooses to pass (typically `userId` and the raw
`message`); there is no formal TypeScript/JSDoc interface or plugin registry — adding a
skill means writing a matcher + handler function and manually wiring both into the
if-else chain in `getLocalSkillReply`. A skill must return a non-empty string to short-
circuit Gemini, or `""`/throw to fall through (calculator and weather explicitly
`catch` and return `""` or a friendly error string rather than let exceptions bubble).

**Skill summaries**:
- **calculator** (`calculator.js`): matches plain arithmetic expressions, "`X% of Y`", "square root of X"/"sqrt(X)", or an unsupported currency-conversion phrase pattern. Evaluates safely by first regex-validating the expression only contains digits/operators, then runs it through `Function("use strict"; return (...))`. Currency conversion is detected but explicitly answered "not available yet."
- **dailyBrief** (`dailyBrief.js`): triggered by "good morning" / "daily brief" / "plans today" phrasing. Combines today's pending reminders (`reminders.js`), memories tagged as plan-like (keyword match on plan/goal/project/meeting/task/todo/decision/recurring), a weather summary for the user's remembered home location, and a top-news summary — into one spoken paragraph. Returns a plain "no saved plans yet" message if there's nothing personal to report (news alone doesn't trigger a full brief).
- **reminders** (`reminders.js`): matches "remind me…", "set a reminder…", "list reminders", plus a separate "tomorrow I need to…" planning-phrase pattern. Parses a title and a due time (regex for "at/by H:MMam/pm", or defaults: "tomorrow"→9am next day, "tonight"→8pm, else "+1 hour") and inserts into the `reminders` table; listing queries pending reminders sorted by `due_at`.
- **weather** (`weather.js`): matches weather/temperature/forecast keywords. Extracts a location from the message ("in/for/at/around X") or, if the user said "here"/"my location", looks it up from the memory store via `findKnownWeatherLocation()` (keyword-scans memory values for location/city/home/live phrasing). Geocodes via Open-Meteo's free geocoding API, then fetches current + daily forecast from Open-Meteo, and composes either a rain-specific answer or a general conditions summary.
- **news** (`news.js`): matches "news"/"headlines"/"current events"/"what's happening today". Maps the message to a coarse topic (Nigeria/AI/Technology/Business/Sports/top news) and calls the backend's `GET /api/news`, which scrapes Google News RSS server-side. Returns up to 4 headlines as a spoken list.
- **conversationRecall** (`conversationRecall.js`): matches "what did we discuss/decide", "what did I say", "regarding…", "about the…" etc. Queries the user's `messages` table (last 150 rows, optionally date-filtered for "yesterday"/"today"), tokenizes the prompt (stopword-filtered), scores messages by keyword overlap + recency, and stitches the top 5 matches into a snippet-based answer, excluding the current message being answered.
- **memory** (`memory.js`, largest module — see below): `isMemoryRecallPrompt` matches phrases like "what do you remember", "what am I working on", "favorite", "do you remember". `formatMemoryRecallReply()` lists the top 8 memories (by confidence + recency) as a single sentence.

**Memory system in detail** (`memory.js` + backend `/api/memory-review`):
- **Storage model**: each memory is a row in `memories` keyed by `user_id + key` (unique), where `key` is a stable, category-prefixed slug like `preference:dark-mode` or `project:voice-buddy`, and `value` is a natural-language sentence like "The user prefers dark mode." `metadata.category` is one of `personal | preference | project | goal | decision | recurring`.
- **Extraction pipeline** (`rememberFromMessage`, called on *every* non-skill user message, `App.jsx:1253`):
  1. **Regex first pass** (`detectMemoryCandidates`) — fast, local, no network. Matches four patterns: "remind yourself that…", "my X is/are Y", "I prefer/like/love X", "I'm building/working on/creating/developing X", "my goal is/I want to/I plan to X". Produces candidate `{key, value, confidence, metadata}` objects.
  2. **Gemini review** (`POST /api/memory-review`) — the regex candidates are sent to Gemini as hints alongside the raw message; Gemini returns strict JSON deciding `shouldRemember` and a possibly-different/expanded list of `{key, value, category, confidence}`. This is authoritative when it succeeds; `normalizeReviewedMemories()` filters to allowed categories and 8+ character values.
  3. **Fallback**: if the Gemini call throws/times out (`MEMORY_REVIEW_TIMEOUT_MS`, 10s), the code falls back to the raw regex candidates from step 1.
  4. **Dedup against existing memories**: before writing, each candidate is checked against the user's existing memories for an exact key match OR (same category AND ≥55% token overlap between `key+value` strings, via `tokenOverlapScore`) — if found, the candidate reuses the *existing* key so `upsertMemory`'s `onConflict: "user_id,key"` update-in-place semantics avoid duplicate near-identical memories under slightly different keys.
  5. Surviving candidates are `upsertMemory()`'d into Supabase.
- **Retrieval** (`getRelevantMemories`, called right before every Gemini chat call): if the current prompt itself looks like a memory-recall question, returns the 8 most recent memories outright. Otherwise scores all memories by `lexicalScore` (token overlap between memory text and prompt) + `confidenceBoost` (confidence×0.5) + `recentBoost` (linear decay over 90 days ×0.25), keeps only >0 lexical matches, and returns the top 8 (or the 3 most recent if nothing scored). `formatMemoriesForPrompt()` renders them as a bulleted list injected into Gemini's `systemInstruction` (§3, `buildChatRequest`).
- Note: this "memory system" is entirely separate from `conversationRecall.js`, which searches raw message history rather than extracted facts.

## 6. STATE AND DATA FLOW

**React state (in-memory, per browser tab, lost on refresh)**: current `conversation`
object, the `messages` array for that conversation, `input` text, all voice/UI state
(`listening`, `speaking`, `loading`, `assistantMode`, `speakReplies`, `showTranscript`,
`status`, `serviceStatus`/`serviceIssue`, `micPermission`, `vadStatus`, `voiceDebug`).
None of this is itself persisted — it is a live cache of what's in Supabase for the
active conversation, rebuilt from state that Supabase holds durably.

**Supabase (durable, RLS-scoped per user)**: `conversations`, `messages`, `memories`,
`reminders` (see §4). This is the source of truth for chat history and long-term facts.

**Conversation load/save cycle**:
- On mount (and whenever `user.id` changes), `restoreConversation()` [App.jsx:349] calls
  `loadMostRecentConversation(user.id)` [conversations.js:24], which fetches the user's
  single most-recently-`updated_at` conversation and all its messages, and seeds React
  state. There is no conversation *list*/switcher UI — the app always resumes the one
  latest conversation. "New Chat" (`startNewChat`) creates a fresh `conversations` row
  and clears `messages` client-side.
- Every user message and every assistant reply is saved to `messages` **as it happens**
  (`saveMessage` before the Gemini call, `saveAssistantReply` after) — not batched — so
  a page refresh mid-conversation loses nothing already sent/received, only in-flight
  state (a spoken-but-not-yet-saved reply, or a half-spoken utterance).
- `updateConversation` bumps `updated_at` after each assistant reply (so
  "most recent conversation" ordering stays correct) and re-titles a still-"New
  conversation" from the first user message (`generateConversationTitle`, first 8 words,
  ≤60 chars).

**Auth gating**: `main.jsx` wraps `<App/>` in `<AuthProvider>`. `AuthProvider` (
`auth/AuthProvider.jsx`) calls `supabase.auth.getSession()` once and subscribes to
`onAuthStateChange`; it exposes `{user, loading, signIn, signUp, signOut}` via context.
`App.jsx`'s default export reads `useAuth()`: while `loading` it shows a spinner-only
screen; if no `user`, it renders `<AuthForm/>` (email/password login or signup, with a
handled edge case where Supabase signup succeeds but requires email confirmation before
a session exists); once a `user` exists, it renders the full `AssistantApp`. If Supabase
env vars are missing/malformed, `supabaseConfigured` is `false` (`lib/supabase.js`),
`supabase` is `null`, `loading` is forced `false`, and the app permanently shows the
auth form with an inline "Supabase is not configured" error on submit.

**Streaming render**: for voice-mode sends, `streamChatMessage()` [lib/api.js:61] reads
the backend's NDJSON stream line-by-line and invokes an `onChunk(text)` callback per
`{type:"chunk"}` line; `App.jsx`'s `handleSendMessage` wires that callback to
`streamingSpeaker.push(chunk)` [App.jsx:1263], which buffers partial text and flushes
complete sentences to `speak()` as soon as they're available (`takeCompleteSpeechChunks`)
— so Heney starts talking before Gemini has finished the full reply. The full concatenated
reply is saved to Supabase once, after `streamingSpeaker.finish()` resolves (all queued
sentence audio has played). For non-voice text chat, streaming is used only to fetch the
reply faster/more resiliently (with `/api/chat` as a non-streaming fallback) — the UI
does not incrementally render partial Gemini text into the chat bubble; the full `reply`
string is written to state only after the whole stream (or fallback call) completes.

## 8. DEPLOYMENT REALITY

**Frontend**: `vercel.json` at the repo root sets `buildCommand: npm run build`,
`outputDirectory: dist`, `installCommand: npm install` — a static Vite build deployed to
Vercel. It defines no rewrites/redirects and no serverless functions, so Vercel serves
only static assets; it does not proxy `/api/*` in production (that proxy is a Vite
*dev-server-only* feature in `vite.config.js`, not something Vercel replicates from
`vercel.json`). This means **`VITE_API_BASE_URL` must be set in Vercel's env vars**
pointing at wherever the Express backend actually runs, or every API call in production
will 404/hit the wrong host.

**Backend**: no deployment config for the backend exists in this repo (no
`Dockerfile`, `railway.json`, `render.yaml`, or `Procfile` found). The only signal for
where it runs is the `RAILWAY_SERVICE_NAME` env var check in `/api/status`
(server.js:220), suggesting the intended host is **Railway**, but this is inferred, not
configured in-repo — **unverified** beyond that one string check.

**What works locally but is fragile/breaks in production or on a phone**:
- **Wide-open CORS + zero backend auth** (§3, §9): in production this means anyone who
  discovers the backend URL can consume your Gemini/ElevenLabs quota from any origin —
  not merely a local-dev convenience gap.
- **Mic + HTTPS**: `navigator.mediaDevices.getUserMedia` and the Web Speech API require
  a secure context — `localhost` is exempt, but the production frontend must be served
  over HTTPS (Vercel gives you this by default) or the mic/voice features silently
  fail. If the backend is on plain HTTP, mixed-content blocking would also break
  `/api/stt`/`/api/tts` fetches from an HTTPS frontend — the backend host must also be HTTPS.
- **Browser support**: Web Speech API (`SpeechRecognition`) is Chrome/Edge-only in
  practice (per CLAUDE.md, and consistent with the `window.SpeechRecognition ||
  window.webkitSpeechRecognition` feature-detect in `App.jsx:25-29`); on unsupported
  browsers (Firefox, most non-Chromium mobile browsers) `speechSupported` is `false`
  and the mic button/Assistant Mode toggle are disabled — the app degrades to
  text-only chat, but this isn't flagged prominently in the UI beyond a disabled
  button.
- **VAD asset loading**: `@ricky0123/vad-web` loads `.onnx`/`.wasm` files from
  `/public/vad/` at runtime via a hardcoded `baseAssetPath: "/vad/"`. If the production
  static host doesn't serve `public/` at the site root exactly as Vite copies it
  (verified present: `public/vad/*.wasm`, `*.onnx`, `vad.worklet.bundle.min.js`), VAD
  silently fails to load and the app falls back to the Web-Speech-only turn-detection
  path (`vadStatus: "failed"`) — degraded but not broken.
- **PWA manifest with no service worker**: `public/manifest.webmanifest` makes the app
  "installable" (add-to-homescreen), but no service worker/offline caching was found in
  this repo — an installed PWA still requires a live network connection; there is no
  offline mode despite the manifest implying an app-like install experience.
- **Dev-only Supabase proxy**: `vite.config.js`'s `/supabase` proxy and
  `lib/supabase.js`'s `viteEnv.DEV` branch only apply in the Vite dev server. In
  production the browser calls `VITE_SUPABASE_URL` directly, relying on Supabase's own
  CORS allowances for the anon key — this should work out of the box but is a
  different code path than what's exercised in local dev, so a dev-only bug class
  (e.g. auth redirect URLs, CORS) could surface only after deploying.
- **No conversation list UI**: because `loadMostRecentConversation` always loads the
  single latest conversation, older conversations are retained in Supabase but are
  unreachable from the UI — not a production-only issue, but worth knowing before
  assuming "no chat history" means data loss.

   surface (Gemini/ElevenLabs proxying + `tool_runs` audit logging), not a backend proxy

9. **Two dead Supabase tables remain**: `profiles`, `calendar_events`, `news_preferences`
   — full schema + RLS + indexes + triggers with zero referencing code (`tool_runs` is no
   longer in this list — see #5 above). Either finish the features they imply or drop them.
10. **`App.jsx` is 1743 lines** doing UI, three overlapping turn-detection state
   machines (Web Speech events, VAD callbacks, and a silence-timeout fallback), TTS
   playback, service-status polling, and conversation persistence orchestration all in
   one component with ~30 `useRef`s. The ref-mirror pattern (documented in CLAUDE.md) is
   a deliberate, necessary workaround for stale closures in long-lived speech callbacks,
   but the file would benefit from splitting into hooks (`useVoiceRecognition`,
   `useAssistantMode`, `useSpeechSynthesis`) purely for maintainability — same behavior,
   less surface area to reason about per change.
11. **`backend/server.js` is now ~1050 lines** (grew from 795 in Phase 0 — auth, CORS,
   rate limiting, and audit logging were added inline rather than split into modules)
   mixing route handlers, three different external-API error-classification heuristics
   (Gemini quota, ElevenLabs quota, ElevenLabs safe-reason), RSS-scraping/XML-parsing
   logic (`extractRssTag`, `decodeXml`), and now auth/rate-limit/audit-log
   infrastructure, all in one file with no router/module split. A reasonable next step,
   not done here per the "minimal diffs" constraint of this pass.
12. **`memory.js` is 452 lines** combining regex-based fact extraction, Gemini-based
   extraction, dedup-via-token-overlap, Supabase CRUD, and prompt-relevance ranking in
   one module — the two extraction paths (regex vs Gemini) have separately-maintained
   category/allow-lists that could drift out of sync (both currently list `personal,
   preference, project, goal, decision, recurring` identically, but nothing enforces
   they stay that way).
13. **Fragile voice pipeline edge cases**: `SELF_INTERRUPT_GUARD_MS` (450ms) and
    `TURN_END_GRACE_MS`/`FALLBACK_SILENCE_DELAY_MS` are hand-tuned magic numbers to stop
    Heney's own TTS audio from re-triggering the mic (echo/barge-in false positives) —
    this is inherently timing-sensitive and likely to misbehave on slower devices,
    Bluetooth audio (which adds latency), or with echoCancellation disabled by the OS.
    `/api/stt` failures silently fall back to the (often lower-quality) Web Speech
    transcript with only a `console.warn`, which could produce confusing mismatches
    between what the user said and what gets sent to Gemini with no user-visible signal
    beyond the general "ElevenLabs issue" status pill. **Not touched in Phase 0**, per
    explicit instruction to leave the voice pipeline alone.
14. **`safeEvaluate()` in `calculator.js` uses `Function(...)` on user input.** It's
    guarded by a strict regex (`/^[\d\s+\-*/().%^]+$/`) allowing only digits/operators
    before constructing the function body, which appears to close the obvious
    injection vector, but dynamic code execution driven by chat input is worth a second
    look if the regex is ever loosened.
15. **`/api/tool-run` is a new, lightly-protected write path**: it's authenticated and
    accepts arbitrary `toolName`/`input`/`output`/`error` strings from the frontend,
    trusting the caller to self-report accurately (there's no server-side whitelist of
    valid `toolName` values). It is not rate-limited (Part 3 only specified chat/tts/stt),
    so a compromised/buggy frontend session could flood a user's own `tool_runs` table —
    low severity since it can only write rows scoped to the caller's own `user_id` (RLS
    would enforce this even without the admin client, and the admin client route still
    only ever inserts `req.user.id`), but worth tightening if `tool_runs` becomes
    load-bearing for anything beyond debugging/audit visibility.

## 10. EXTENSION POINTS

**(a) Add a new skill** (e.g. a "jokes" skill):
1. Create `src/lib/jokes.js` exporting `isJokePrompt(message): boolean` and
   `getJokeReply(message): string | Promise<string>` (follow the pattern in
   `calculator.js` for a sync skill or `weather.js` for an async one that hits an
   external API).
2. In `src/lib/skills.js`, import both and add an `if (isJokePrompt(message)) { ... }`
   branch inside `getLocalSkillReply()` — position matters, since the first matching
   skill wins and some existing matchers are broad (e.g. `news.js`'s bare `/\bnews\b/i`).
3. No registry, no config file, no backend change needed — skills are purely
   frontend/Supabase-side and never touch `backend/server.js` unless they need a new
   external-API proxy route (see (b)).

**(b) Add a new API endpoint** (e.g. a currency-conversion proxy the calculator skill
currently stubs out):
1. Add `app.get("/api/fx", async (req, res) => { ... })` (or `.post`) in
   `backend/server.js`, following the existing pattern: read `req.query`/`req.body`,
   call the external service with `fetch`, classify/handle errors with a
   `serviceErrorResponse(...)`-style helper, `res.json(...)`.
2. Add the corresponding client call in `src/lib/api.js` (a `fetch(apiUrl("/api/fx?..."))`
   wrapper, mirroring `getNewsReply`'s pattern of calling through `apiUrl()` so it works
   both via the Vite dev proxy and `VITE_API_BASE_URL` in production).
3. If it needs a new env var/API key, add it to `backend/.env.example` and read it via
   `process.env.X` near the top of `server.js` alongside the other config constants.

**(c) Add a new database table with RLS** (e.g. finishing the dead `calendar_events`
table, or a genuinely new one):
1. Add a new file under `supabase/migrations/` (don't edit the existing one — it's
   already been "reviewed... in the Supabase SQL Editor" per its own header comment;
   treat migrations as append-only). Follow the existing table shape: `id uuid primary
   key default gen_random_uuid()`, `user_id uuid not null references auth.users(id) on
   delete cascade`, `created_at`/`updated_at timestamptz default now()`.
2. `alter table public.<table> enable row level security;` then add
   `create policy "Users can manage own <table>" on public.<table> for all using
   (user_id = auth.uid()) with check (user_id = auth.uid());` — matches the pattern
   used for `memories`/`reminders`/`calendar_events`/`news_preferences`/`tool_runs`.
3. If it needs `updated_at` auto-maintenance, add
   `create trigger set_<table>_updated_at before update on public.<table> for each row
   execute function public.set_updated_at();` (reuses the existing shared function).
4. Apply the migration to the Supabase project (**unverified**: no migration-runner
   script found in this repo — likely applied manually via the Supabase SQL editor or
   `supabase db push`, consistent with the migration file's own header comment).
5. Add a new `src/lib/<table>.js` with `supabase.from("<table>")` CRUD functions,
   following `reminders.js`/`conversations.js` as templates.

**(d) Add a new Gemini tool/function call**: there is currently **no Gemini
function-calling/tools configuration anywhere in this codebase** — `buildChatRequest()`
(server.js:549) only sets `model`, `contents`, and `config.systemInstruction`; no
`tools`/`functionDeclarations` array is passed to `ai.models.generateContent`. All
"tool use" today is the local skills system (§5), which intercepts *before* Gemini is
ever called, not real Gemini-native function calling. To add real Gemini tool-calling:
1. Define a `functionDeclarations` array (name, description, JSON-schema parameters)
   and pass it as `config.tools` in `buildChatRequest()` (`backend/server.js`).
2. Both `/api/chat` and `/api/chat/stream` handlers would need new logic to detect a
   `functionCall` part in Gemini's response, execute the corresponding server-side
   logic, and send a follow-up `generateContent`/`generateContentStream` call with the
   function's result as a `functionResponse` part before returning to the client — this
   is a non-trivial protocol change to both streaming and non-streaming paths, not a
   one-line addition, since neither currently branches on response part types beyond
   plain text (`response.text`).
3. Decide the overlap with the existing skills system: today skills pre-empt Gemini
   entirely; native Gemini tools would let Gemini itself decide when to invoke a
   capability mid-conversation, which is a different (and currently unbuilt) control
   flow.
